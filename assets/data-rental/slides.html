Confidential Data Rental

Rent your data without handing it over

A data owner's records can be decrypted only inside a Google Confidential VM running the one computation the owner approved. Shown working live on Google Cloud in October 2026.

Business overview

Opening line: today, renting data means handing over a copy and trusting a contract. This deck shows a way to rent data where the copy never leaves a locked box, and the box opens only for the computation the owner approved.

Our vision

Data is the fuel of the AI era

Every model, every forecast, every assistant runs on it. But fuel has one property data lacks: when you sell a barrel, you no longer have the barrel. Share a dataset and the buyer keeps it forever. So the most valuable data in the world sits unused, locked inside the organizations that hold it.

We want data to be rented the way fuel is sold: by the use, under the owner's terms, without the owner ever losing it.

The analogy, and its one flaw. Oil changes hands; data gets copied. Our platform gives data the property fuel has: it can be used once, by one approved process, and the owner keeps it.

The problem

Renting data today means giving it away

The data owner

Hands over a copy and relies on a contract. Once the copy is out, nothing brings it back.

The computation party

Its method is its edge. Sending that code to the owner's systems exposes it.

The platform in between

Whoever runs it can see both sides, so it becomes the target and the liability.

Each side has to trust the other, and both have to trust the platform. That is why most valuable data is never rented at all.

Three parties, three reasons the deal does not happen. The fix has to remove the need for trust on all three, not just one.

The idea

The data opens only for the computation the owner approved

The data is encrypted before it leaves the owner. The computation is sealed into an image with a fingerprint. The owner approves that fingerprint, and the key that unlocks the data is released only to a Google Confidential VM that proves it is running exactly that image.

The fingerprint is a digest: a hash of every byte of the image. Change one line of code and the fingerprint changes, so the key stays locked.

How it works

No single party, including the platform, sees both the data and the computation. The data is readable only inside the sealed VM, by the approved code.

The important row is the platform operator. Even we, running the service, see only ciphertext.

How it works

A rental in five steps

01

Promise

The computation party uploads its code. It becomes an image, and the image's fingerprint is published.

02

Approve

The data owner approves that fingerprint. Their key policy on Google Cloud now names it.

03

Encrypt

The data is encrypted. The key sits in Google Cloud KMS and is released only under that policy.

04

Run

A Confidential VM boots the image. Google attests it, the fingerprint matches, the key is released.

05

Result

The computation runs inside the VM. The result goes to the computation party, sealed to its key.

Once the owner has approved the fingerprint, every step is automatic. A run takes about two minutes, and the VM is deleted afterwards.

Walk the five steps left to right. The owner acts once, at step two. Everything after that is enforced by Google Cloud, not by people.

The guarantee

Why this holds, in plain terms

Encrypted everywhere

At rest, in transit, and in use: the processor encrypts the VM's memory, so not even the cloud provider can read it.

Measured, not promised

Google's hardware measures the running image and signs a statement of its fingerprint. No party can edit that statement.

The owner holds the key policy

The key is released only when the signed fingerprint equals the one the owner approved. The platform cannot override it.

Any change is refused

One changed line gives a different fingerprint. The key stays locked, and not a single record is read.

If someone asks "why should I trust this?", the answer is the second card: nobody vouches for the code, the hardware measures it.

Proof

What the live run showed

Run 1, the approved image. Google attested the VM, the key was released, and the computation party received statistics over 30,000 records.

Run 2, one line changed. A different fingerprint, so Google's key release refused it. Not a single record was decrypted.

What's next

From demo to service

Harden for real data

Production VM images instead of the demo's debug image. A key and policy per data owner. Each party encrypts and verifies on its own machine, so the platform only relays ciphertext.

Train models, not just statistics

A second mode trains machine-learning models under a privacy budget, so even the trained model cannot give away a record. GPU support follows.

Run it as a service

Public hosting with accounts, usage limits and billing. One Confidential VM per run, deleted when the run ends.

Everything shown today runs on standard Google Cloud services. No custom hardware, and no special agreements with the cloud provider.

Close on the last line: this is built from services anyone can buy today. The remaining work is engineering, not research.
